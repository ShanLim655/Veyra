# Veyra 1.2.5 — Bug Fixes, Performance, Notifications & Muting

Release theme: fix reported chat bugs, make the database/API faster, ship real push notifications for Android and desktop (no third-party app required), and add per-channel muting.

---

## 1. Bug: reactions fail on messages (incl. media/voice)

**Reported:** adding a reaction to a message, image, video, or voice message fails.

**Root cause (confirmed):** `message_reactions.message_id` has a foreign key to `messages(id)` only, and `canInsert` in `server/data.mjs` verifies membership via `messages ⋈ conversation_members`. Reactions on `global_messages` and `announcement_messages` fail on both checks. DM reactions should work — verify and reproduce first.

**Work:**
- Reproduce on each surface: DM, group, Global Chat, announcement, and on media/voice messages specifically.
- Schema: make `message_reactions.message_id` polymorphic (drop the `messages`-only FK in both `schema.sql` and `schema.postgres.sql`, or add separate nullable FKs / a `message_table` discriminator column).
- `server/data.mjs` `canInsert`/`policy`: accept reactions when the target exists in `messages` (membership check), `global_messages`, or `announcement_messages` (any user).
- `server/realtime.mjs` `recipientsFor`: resolve reaction targets across all three tables so reaction events reach the right users (currently looks up `messages` only).
- Frontend `fetchReactions`/realtime merge: confirm reactions load for global/announcement messages.
- Regression test: react → unreact on each surface.

## 2. Bug: duplicate DM conversations on fast friend-request accept

**Reported:** accepting a friend request quickly creates two DM conversations.

**Root cause (confirmed):** `ensureDirectMessage` in `server/rpc.mjs` does `SELECT existing → INSERT` with no lock or unique constraint; two concurrent accepts (both directions pending) both see "no DM" and both insert. Called from `server/data.mjs` friend-request accept path.

**Work:**
- Add an atomic dedupe mechanism. Preferred: a `dm_pairs` table with `UNIQUE(sorted_user_low, sorted_user_high)` — insert-or-fetch inside a transaction; create the conversation only for the winner. Requires schema change in both `schema.sql` and `schema.postgres.sql` + `db:migrate`.
- Alternative if schema change is undesirable: dialect-aware advisory lock (`GET_LOCK` / `pg_advisory_xact_lock`) around check+insert.
- Audit `get_or_create_dm` RPC for the same race.
- Regression test: two simultaneous accepts → exactly one conversation.

## 3. Performance: database/API "slow as heck"

No single confirmed bottleneck yet — investigate, then fix.

**Investigate:**
- Where latency is: Vercel cold starts, DB round-trips per request, remote Altare MariaDB latency, or query plans. Add timing logs or run `EXPLAIN` on hot queries.
- `/api/data` overhead: `canInsert`/policy subqueries per row, `columnsFor` caching, Redis read-cache actually enabled in production (`REDIS_URL` is now configured — verify it's active and hit-rate is sane).
- Message history fetch: page size, media signing batching, profile/reaction fan-out queries.
- Realtime path: change-detection polling frequency, recipient resolution queries per change.
- Serverless pooling: pool size cap of 2 × concurrent Vercel instances vs Altare connection limits; consider `maxDuration`/region colocation.

**Likely fixes (confirm during investigation):**
- Enable/verify Redis read caching for hot `select` paths.
- Composite indexes if `EXPLAIN` shows scans (candidates: `messages(conversation_id, created_at)` exists — check `message_reactions(message_id)`, `conversation_members(user_id)`, `friend_requests` lookups).
- Batch or cache per-request lookups (admin checks, column metadata).
- Reduce realtime DB polling if applicable.

## 4. Push notifications — Android + desktop, no extra app

**Android: Firebase Cloud Messaging (FCM)**
- Add `@capacitor/push-notifications`; request permission in-app; `google-services.json` in `android/app/`; free Firebase project.
- Client stores FCM token in existing `native_push_tokens` (`platform='android'`, `device_id`).
- Server: extend `server/notifications.mjs` fan-out to send via FCM HTTP v1 API (service-account JSON in env, e.g. `FCM_SERVICE_ACCOUNT_JSON`); keep ntfy as optional fallback.
- Respect `notification_preferences` per user/channel.

**Desktop (Electron/Windows)**
- Phase 1: tray-resident app — minimize to tray on close, deliver `new Notification()` from the main process driven by the existing Supabase Realtime message events. Works with zero new infra; no notification when fully quit.
- Phase 2 (optional): evaluate OneSignal or WNS for closed-app push.

**Web (optional later):** Web Push + VAPID service worker on the Vercel HTTPS deployment.

## 5. Mute button — groups, DMs, Global Chat

**Schema:**
- `conversation_members.muted BOOLEAN NOT NULL DEFAULT FALSE` (per-user, per-conversation) — both schemas.
- Global Chat has no membership row — add `profiles.global_muted BOOLEAN NOT NULL DEFAULT FALSE` (or reuse a settings JSON if one exists).
- Announcement channel: decide scope (likely same global flag or separate).

**Backend:**
- `notifications.mjs`: skip muted conversations/users when fanning out ntfy/push.
- `data.mjs` policy already scopes `conversation_members` writes to members — verify mute toggles are allowed for self.
- Optional: `muted_until` timestamp instead of boolean if timed mute is wanted (keep simple: boolean first).

**Frontend:**
- Muted indicator icon in chat list + chat header.
- Toggle in chat header menu / group settings / DM profile menu / global chat settings.
- Bell icon state (filled = unmuted, slash = muted).
- Suppress in-app toast/banner for muted channels (decide: mute notifications only, or also sounds — spec: notifications + sounds, messages still arrive).
